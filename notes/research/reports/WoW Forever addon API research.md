# Capture souls in the open world first

Quantum-Seer is buildable on WoW Forever 1.60.1, but three assumptions in PLAN.md §3 need to change before Phase 1. First, **Forever changed Drain Soul so that damage alone can produce a shard**. A new shard no longer means a kill, so the plan's rule that a shard arriving inside a capture window is a kill will mint cards for mobs that escaped. Second, **Forever is a Midnight-family client ("Camelot"), not a Classic Era client**. Its generated API docs mark `UnitGUID`, `UnitName` and `UnitCreatureType` as secret whenever an NPC's identity is restricted, while `UnitLevel`, `UnitClassification` and `UnitIsDead` carry no secret tag. In-client reports from local addons say target identity stays readable in open-world combat. Three separate addon authors say it is hidden inside dungeons and raids. Third, **`SetCreature(npcID)` is the wrong primary renderer**. Capture a creatureDisplayID instead and render with `SetDisplayInfo`, with `SetPortraitTextureFromCreatureDisplayID` for thumbnails. On the delete side, the sources settle most of the plan's questions: one delete per real key press, nothing from events or in combat, and bag-to-bag moves that need no key press. The open items are `/click` on a plain button, `ExecuteFrameScript` and world clicks. On novelty, both halves of the idea already exist on Forever. Adventure Journal turns kills into shiny 3D cards in a binder, and Soul Journal and Soul Provenance record Drain Soul victims. Quantum-Seer's distinct position is the combination: Drain Soul capture, TCG mechanics (foil, 1st Edition, sets) and shard management in one addon.

Status labels used throughout: **confirmed** means seen in Blizzard's generated docs or UI source on the `forever` branch (1.60.1 build 70938), or in a quoted Blizzard statement. **Reported** means stated by an addon author, wiki or forum, including in-client findings from the local reference addons. **Unknown** means no reliable evidence. Citations to `reference/` are local clones of MIT addons and are not public URLs.

## Forever is Midnight with a level-60 skin, so retail rules apply

The most important context is that Forever is not the 1.15 Classic Era client. Blizzard said that "WoW Forever shares Mainline WoW's UI architecture, including the vast majority of APIs available in 12.1.5" and that "the addon disarmament changes introduced in Midnight, including secrets, will also be active in Forever" ([warcraft.wiki.gg Patch 1.60.1 API notes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes)). The UI source shows `WOW_PROJECT_ID = WOW_PROJECT_CAMELOT` (18). Mainline files load with Camelot overrides ([wow-ui-source forever](https://github.com/Gethe/wow-ui-source/tree/forever)). `WOW_PROJECT_ID` was 1 on an earlier beta build and 18 later, so code should **probe for APIs instead of branching on project ID** ([wowforeverguides](https://wowforeverguides.com/addons/developers)). Beta build 69913 also lacked the `GetSpellInfo` and `GetItemInfo` globals ([wowforeverguides](https://wowforeverguides.com/addons/developers)). This confirms the plan's `C_Spell`/`C_Item` shims.

Two Forever-specific changes affect the data model. From Beta 5 (70425), creature GUIDs have their **server-ID and spawn-ID fields obfuscated**. They "remain stable and unique within your own session" ([wiki notes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes)). A GUID is therefore only a session-scoped dedupe key. The note names only server and spawn IDs, so the npcID (field 6) is probably intact, but no source verifies that. Second, characters have surnames: `UnitNameUnmodified("player")` returns name and surname. AceDB on Forever already depends on this ([AceDB in SoulShardForever](../../../reference/SoulShardForever/Libs/AceDB-3.0/AceDB-3.0.lua)). That supports the plan's "First Surname" helper.

### Secret values: what the docs say and what players observe

The Forever docs put these predicates on unit APIs ([forever API docs](https://github.com/Gethe/wow-ui-source/tree/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated)):

| API | Forever annotation | Readable for a hostile NPC? |
|---|---|---|
| `UnitGUID`, `UnitCreatureType`, `UnitCreatureFamily`, `UnitClass`, `UnitRace`, `UnitTokenFromGUID` | `SecretWhenUnitIdentityRestricted` | Not when identity is restricted |
| `UnitName` | `SecretWhenUnitNameIdentityRestricted` | Same, except players in PvP |
| `UnitLevel`, `UnitClassification`, `UnitIsDead`, `UnitExists` | No secret-return tag | Yes, per docs |
| `UnitHealth` | `SecretReturns` (always) | No arithmetic |
| `UnitHealthMax` | Secret for non-player-controlled units | No |

The predicate reads: "Guarded APIs and events produce secret values when the unit isn't player-controlled or in the party/raid" ([forever API docs](https://github.com/Gethe/wow-ui-source/tree/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated)). Taken literally, that covers every hostile mob at all times. The wiki's Midnight page instead says `UnitName` is secret for non-players "while in combat" ([warcraft.wiki.gg Secret Values](https://warcraft.wiki.gg/wiki/Secret_Values)), which implies the predicate only applies while a restriction is active. The empirical Forever evidence points the same way. Warlock Tools Forever's notes say "cast events, target name, and `UnitGUID` are readable in combat" for the player's casts. The same notes say target and focus GUIDs read cleanly while **nameplate GUIDs were sometimes secret** ([WTF AGENTS.md](../../../reference/WarlockToolsForever/AGENTS.md)). Instances are different. KillDex says "Blizzard hides which mob died inside instances on Midnight and WoW Forever" ([CurseForge KillDex](https://www.curseforge.com/wow/addons/killdex)). Yonder says Forever "hides creatures inside Forever dungeons and raids from addons" ([CurseForge Yonder](https://www.curseforge.com/wow/addons/explorers-field-journal)). Soul Journal says it recovers names hidden in combat or instances after combat, from the targeted corpse or the XP message, and otherwise logs a "Lost Soul" ([CurseForge Soul Journal](https://www.curseforge.com/wow/addons/soul-journal)). The working model is therefore: **open-world target identity is readable in combat (reported); instance identity is secret (reported by three authors); level and classification are always readable (confirmed in docs)**. One beta report claims `UnitExists` and `UnitCanAttack` can return secret booleans, contradicting the docs ([wowforeverguides](https://wowforeverguides.com/addons/developers)). Guard every read anyway.

The plan already guards every read with `issecretvalue`. What the sources add are the rules for what to do with a secret once you have it. Addon code may store, pass and concatenate secrets, and pass them to setters such as `FontString:SetText`. It may not compare them, use them as a table key, take `#` of them, do arithmetic on them, or test a secret boolean. Each of these is an immediate Lua error. **A secret never becomes readable later.** You must re-query after the restriction lifts ([warcraft.wiki.gg Secret Values](https://warcraft.wiki.gg/wiki/Secret_Values)). No source says whether secrets survive being written to SavedVariables, so the capture record must never persist one. The confirmed `C_RestrictedActions` surface offers a useful hook. `ADDON_RESTRICTION_STATE_CHANGED` fires with state `Activating` before enforcement begins, so a handler can snapshot the target just before combat locks it ([forever API docs](https://github.com/Gethe/wow-ui-source/tree/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated)). The CVars `addonCombatRestrictionsForced` and `addonEncounterRestrictionsForced` simulate restrictions on Midnight ([warcraft.wiki.gg Secret Values](https://warcraft.wiki.gg/wiki/Secret_Values)). Whether they work on Forever is unknown, but they would make Phase 0 much faster.

### Spell events and kill signals

`UNIT_SPELLCAST_CHANNEL_START`, `_STOP` and `_SUCCEEDED` carry `SecretWhenUnitSpellCastRestricted`. That predicate makes payloads secret only when the caster is not the player or pet, but "individual spells may be flagged as never or always secret, which takes priority" ([forever API docs](https://github.com/Gethe/wow-ui-source/tree/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated)). Warlock Tools Forever nonetheless saw a **secret spellID on the player's own `CHANNEL_STOP`** and now refuses the capture window when that happens ([WTF Shards.lua](../../../reference/WarlockToolsForever/Shards.lua)). Matching by spell name (the plan's choice) does not fix this. `C_Spell.GetSpellName` of a secret ID presumably returns a secret. The robust design is to set a "channeling Drain Soul" flag on START and clear it on any STOP regardless of payload. `UnitChannelInfo("player")` can serve as a cross-check. `GetSpellCastSecrecy(spellID)` in the client reveals whether Drain Soul is flagged always-secret.

`COMBAT_LOG_EVENT_UNFILTERED` is unavailable. The docs tag it `HasRestrictions`, and merely registering it raises `ADDON_ACTION_BLOCKED` on Forever ([forever API docs](https://github.com/Gethe/wow-ui-source/tree/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated); [WTF AGENTS.md](../../../reference/WarlockToolsForever/AGENTS.md)). Two events replace it for kill attribution, and both are confirmed present: **`PARTY_KILL(attackerGUID, targetGUID)` and `UNIT_DIED(unitGUID)`**. Both carry the identity-restricted secret tag, so they are reliable in the open world and probably blind in instances ([forever API docs](https://github.com/Gethe/wow-ui-source/tree/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated)). The plan does not use either event. It should, because they distinguish a kill from a damage-only shard (next section).

## Forever's shard rules break the "new shard means a kill" assumption

PLAN.md §3.1 links every shard that arrives inside a Drain Soul or Shadowburn window to the snapshotted enemy's death. On Forever that is false. The Forever spellbook text from beta build 69893 reads: "Damaging a non-trivial target can generate a Soul Shard; a qualifying Drain Soul kill guarantees one" ([foreverwisp](https://www.foreverwisp.com/guides/wow-forever-warlock-beta-levelling-changes)). The wiki gives the same rule ([warcraft.wiki.gg Drain Soul](https://warcraft.wiki.gg/wiki/Drain_Soul)). Blizzard's November 2 development notes, quoted on the forums, say that **the chance to grant a shard on damage "has been reduced significantly"**. That reduces the effect but does not remove it ([Blizzard forums](https://us.forums.blizzard.com/en/wow/t/latest-warlock-changes/2399400)). Shadowburn also differs. On Forever, a non-trivial target dying within **8 s** grants a shard, against 5 s in Classic ([warcraft.wiki.gg Shadowburn](https://warcraft.wiki.gg/wiki/Shadowburn)). The plan's 9 s window is a sensible margin. Shadowburn also costs a shard, so the count drops on cast and may rise later. The watcher must treat the net change carefully. Classic's "must yield XP or honor" condition becomes "non-trivial" on Forever. That probably means non-grey, but no source confirms it.

Soul Journal already handles damage shards. It calls them "Sparks", partial shards from Drain Soul ticks, and marks a soul "slipped away" as a faint ghost when the target escapes ([CurseForge Soul Journal](https://www.curseforge.com/wow/addons/soul-journal)). Quantum-Seer needs an equivalent split. A shard that arrives while the target is alive and the channel continues is a damage shard. A shard that arrives with `UnitIsDead("target")` true, or after a `PARTY_KILL` naming the player, is a kill. The first can become a lesser "Echo" card or a foreign shard. Only the second should mint a full card, so that "Captured 12×" means 12 kills. The kill fallback chain is: `PARTY_KILL` when GUIDs are readable; otherwise channel ended, plus `UnitIsDead("target")` (no secret tag), plus a shard delta inside the window.

The remaining shard facts are mostly unchanged from Classic. Soul bags still exist, and a Forever "Felblood Soul Bag" (30 slots) is listed in community databases ([metaforge](https://metaforge.app/wow-forever/database/containers?quality=4)). Shards still do not stack, according to unresolved player requests ([Blizzard forums](https://us.forums.blizzard.com/en/wow/t/warlock-soul-shards-keep-the-mechanic-drop-the-bag-tax/2368623)). The Forever spell IDs for intermediate Drain Soul and Shadowburn ranks were not verified. They can be pulled from the wago.tools `wowf` SpellName table.

## One delete per real key press, out of combat, outside instances

The delete rules are the best-documented part of the research. The general rule comes from the wiki: `DeleteCursorItem` has needed a hardware event since retail 9.0.2, and since 9.1.5 it is "limited to deleting a single item per hardware event" and blocked from `/run`, `/script` and `loadstring` ([warcraft.wiki.gg DeleteCursorItem](https://warcraft.wiki.gg/wiki/API_DeleteCursorItem)). On Forever the API is tagged `HasRestrictions` ([forever GameCursorDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/GameCursorDocumentation.lua)). Shard Grid reports that "a second DeleteCursorItem in the same key press is refused" ([ShardGrid.lua](../../../reference/shard-grid/ShardGrid.lua)). Warlock Tools Forever reports that deletes from event handlers are blocked in and out of combat. It also reports that **a key-press delete was blocked inside a dungeon**, so the plan's restriction check must include the Map, Encounter, ChallengeMode and PvPMatch types as well as Combat ([WTF TESTING.md](../../../reference/WarlockToolsForever/TESTING.md)). Forever also adds an API the plan doesn't mention: **`C_Item.DeleteItem(itemGUID)`**, also `HasRestrictions`. Blizzard's own delete popups use it ([forever ItemDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/ItemDocumentation.lua)). If addons can call it from a key press, it removes the cursor pickup step.

The `/click` dispute has a source-level explanation. On Classic Era, `/click` presses any non-forbidden button. On Forever (and live 12.1.5), it calls `Click()` only if `not button:HasAccessConstraints()` and the button lacks the `ScriptedInput` forbidden aspect. It also defaults to a release-only click ([forever SlashCommands.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ChatFrameBase/Shared/SlashCommands.lua); [classic_era SlashCommands.lua](https://github.com/Gethe/wow-ui-source/blob/classic_era/Interface/AddOns/Blizzard_ChatFrameBase/Shared/SlashCommands.lua)). Warlock Tools Forever's failed test used **SecureActionButtons**, which plausibly have access constraints ([WTF TESTING.md](../../../reference/WarlockToolsForever/TESTING.md)). SoulShardForever's `/click SSFDelete` targets a **plain insecure button** ([SSF DeleteButton.lua](../../../reference/SoulShardForever/Modules/DeleteButton.lua)). Both claims may therefore be right. This is an inference, so a ten-second test settles it. The same gate applies to the secure `type=click` action, which makes IncoreShards' proxy to `StaticPopup1Button1` doubly doubtful ([forever SecureTemplates.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua)).

`ExecuteFrameScript` is undocumented. The wiki page 404s and it is absent from the generated docs, though Blizzard's UI calls it on every branch ([warcraft.wiki.gg 404](https://warcraft.wiki.gg/wiki/API_ExecuteFrameScript)). Hardware-event state belongs to the input dispatch, not to the function, so a delete run synchronously from a slash handler through `ExecuteFrameScript` should behave like a direct call. That is untested. The plan's options (a) through (c) don't need it, so it is low priority. World clicks remain contested: WTF hooks `WorldFrame` OnMouseDown, while Shard Grid reports refusals "pressed or released" ([ShardGrid.lua](../../../reference/shard-grid/ShardGrid.lua)). Two Forever addons agree that a **propagating keyboard listener works out of combat** ([WTF TESTING.md](../../../reference/WarlockToolsForever/TESTING.md); [ShardGrid.lua](../../../reference/shard-grid/ShardGrid.lua)). The wiki confirms `SetPropagateKeyboardInput` cannot be called by insecure code in combat since 10.1.5 ([warcraft.wiki.gg](https://warcraft.wiki.gg/wiki/API_Frame_SetPropagateKeyboardInput)).

SSF's "server reverts in-combat deletes" claim has **no corroboration**. The better-documented observation is that the in-combat delete is blocked at call time and the shard returns to its bag immediately ([WTF TESTING.md](../../../reference/WarlockToolsForever/TESTING.md)). The policy is the same either way. On detection: blocked events on Forever name the function `UNKNOWN()`, not `DeleteCursorItem()`. Other activity raises them too, such as `SetRaidTarget` and registering CLEU. So the plan should treat **"item still on cursor after the call" as the primary refusal signal** and the event as secondary ([WTF Shards.lua](../../../reference/WarlockToolsForever/Shards.lua)).

Moves are not hardware-gated. `C_Container.PickupContainerItem` carries only `SecretArguments = "AllowedWhenUntainted"` on Forever, with no `HasRestrictions` ([forever ContainerDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/ContainerDocumentation.lua)). SSF and Shard Grid both move shards from events and timers ([SSF Sorter.lua](../../../reference/SoulShardForever/Modules/Sorter.lua); [ShardGrid.lua](../../../reference/shard-grid/ShardGrid.lua)). The real constraint is item locks. Moves are asynchronous, so plan all moves from one snapshot, skip locked slots, and re-run on `BAG_UPDATE_DELAYED` or `ITEM_LOCK_CHANGED`. No source documents a per-frame cap or a combat block on moves, though every addon avoids moving in combat.

## Render cards from a captured displayID, not from SetCreature

Every model API the plan names exists on Forever: `SetCreature(creatureID, displayID=0)`, `SetDisplayInfo`, `SetUnit`, `GetDisplayInfo`, `SetPortraitZoom`, `SetCamDistanceScale`, `ClearModel`, plus ModelScene actors with `SetModelByCreatureDisplayID` ([forever FrameAPICharacterModelBaseDocumentation.lua](https://github.com/Gethe/wow-ui-source/tree/forever)). The PlayerModel script list includes `OnModelLoaded` ([warcraft.wiki.gg PlayerModel](https://warcraft.wiki.gg/wiki/UIOBJECT_PlayerModel)). The weakness is `SetCreature`. Retail developers have reported since 2016 that it draws nothing for NPCs the client has not cached ([WoWInterface](https://www.wowinterface.com/forums/showthread.php?p=314931); [Blizzard forums](https://us.forums.blizzard.com/en/wow/t/display-creature-macro-issue/325634)). Nothing about this is Forever-specific, but the risk applies to a fresh install, a cleared cache, or a shared card. **`SetDisplayInfo(displayID)` resolves through the client-shipped CreatureDisplayInfo table** (14,227 rows in the `wowf` build), so it should not need the creature cache ([wago.tools CreatureDisplayInfo](https://wago.tools/db2/CreatureDisplayInfo/csv?build=1.60.1.70938)). Blizzard's own Vanilla-family quest frame renders NPC portraits this way ([wow-ui-source forever](https://github.com/Gethe/wow-ui-source/tree/forever)). For the 3×3 grid, **`SetPortraitTextureFromCreatureDisplayID(texture, displayID)`** draws a cheap 2D portrait on a plain texture, with no model frame ([warcraft.wiki.gg](https://warcraft.wiki.gg/wiki/API_SetPortraitTextureFromCreatureDisplayID)).

The catch is that **Forever has no unit-to-displayID API**. A search of all Forever API docs found only player, pet-journal, mount and Delves display-ID functions ([wow-ui-source forever](https://github.com/Gethe/wow-ui-source/tree/forever)). The plausible capture route is a hidden PlayerModel: call `SetUnit("target")` at Drain Soul start, then read `GetDisplayInfo()`. This is untested and is the single most valuable model probe. The npcID comes from `C_CreatureInfo.GetCreatureID(guid)` or GUID field 6, and both depend on a readable GUID.

Offline data is thin. The client's Creature DB2 holds only **189 rows** (pets and critters), so wago.tools cannot produce an npcID-to-displayID map for general mobs ([wago.tools Creature](https://wago.tools/db2/Creature/csv?build=1.60.1.70938)). Wowhead has Forever NPC pages but returns HTTP 403 to scripted fetches ([Wowhead](https://www.wowhead.com/forever/npc=299/diseased-young-wolf)). "Creature Display DB" claims Forever support and exposes `GetDisplayIdByNpcId`, but it is All Rights Reserved ([CurseForge](https://www.curseforge.com/wow/addons/creature-display-db)). It can at most be an optional, runtime-detected source, which bends the plan's "no dependency on another author's addon" rule. For card badges, `C_CreatureInfo.GetCreatureFamilyInfo` returns an `iconFile`, but `GetCreatureTypeInfo` returns no icon, so type icons must be shipped ([wow-ui-source forever](https://github.com/Gethe/wow-ui-source/tree/forever)). Forever's family table includes non-vanilla entries: Incubus 302, Felguard 310, Core Hound 312 and Fox 319 ([wago.tools CreatureFamily](https://wago.tools/db2/CreatureFamily/csv?build=1.60.1.70938)).

## Two Forever addons already own each half of the idea

The collection idea is not new on Forever, and the plan should say so. **Adventure Journal** launched in late October 2026 with Forever 1.60.1 support. It turns every defeated creature into a "painted card" in a "binder-style album", shows 3D models, and states that "rarer monsters have shinier cards". It adds a card game, Essences and about 2,000 achievements. It has about 900 downloads and is All Rights Reserved ([CurseForge Adventure Journal](https://www.curseforge.com/wow/addons/adventure-journal)). On the Warlock side, **Soul Journal** (Forever-only, MIT) records the soul behind each Drain Soul or Shadowburn shard. It shows one ghost per page "turning slowly inside a crystal shard", tracks releases with a FIFO assumption, and uses `/souls` ([CurseForge Soul Journal](https://www.curseforge.com/wow/addons/soul-journal)). **Soul Provenance** (Forever and Classic, MIT) gives each soul a permanent Soul Number and a Potency tier mapped from classification (Common, Potent, Greater, Ancient). It adds temperaments, a ledger and trophies, and keeps a backup SavedVariable ([CurseForge Soul Provenance](https://www.curseforge.com/wow/addons/soul-provenance)). KillDex and Yonder cover bestiary-style kill catalogues. KillDex adds export strings and a website ([CurseForge KillDex](https://www.curseforge.com/wow/addons/killdex)).

No addon found combines the halves. None of the soul addons has card mechanics, and Adventure Journal is class-agnostic, with no foil odds, 1st Edition stamps or shard management. Quantum-Seer's pitch is therefore "the Warlock's shard bag is a booster pack": deliberate, skill-gated capture by Drain Soul, published foil odds, 1st Edition stamps, zone and type sets, plus a shard manager that beats the five reviewed ones. Soul Journal and Soul Provenance are MIT. Their capture code is the nearest reference implementation for damage-vs-kill classification and instance-name recovery, and it should be read before Phase 5.

The design literature supports most of §3.3 but questions two choices. The official WoW TCG took its rarity colours directly from item quality ([warcraft.wiki.gg Trading Card Game](https://warcraft.wiki.gg/wiki/Trading_Card_Game)), which matches the plan's tiers. Hearthstone's official odds give each golden Legendary a **0.6% per-pack chance with a 361-pack pity timer**. Hearthstone also gives no duplicate Legendaries until the set is complete ([Hearthstone wiki](https://hearthstone.wiki.gg/wiki/Card_pack_statistics)). The plan's 2.5% Shadow Foil and 0.1% Void Prism are in a reasonable range. They lack a pity counter, though, and at 0.1% most players will never see a Void Prism. Practitioner guidance says visible, fillable sets drive completion and that duplicates need a secondary use ([Yu-kai Chou](https://yukaichou.com/gamification-study/game-design-technique-collection-sets/); [Yu-kai Chou merging loop](https://yukaichou.com/advanced-gamification/merging-loop-duplicate-drops-anticipation/)). That cuts against the plan's "totals only for what we've seen" deferral. Instance-hidden mobs would also need excluding from any denominator. For v2 sharing, `SendAddonMessage` allows a 255-byte message with a per-prefix budget of 10 messages refilling at 1 per second. **Trial and Veteran accounts cannot send addon messages on Forever 1.60.1** ([warcraft.wiki.gg SendAddonMessage](https://warcraft.wiki.gg/wiki/API_C_ChatInfo.SendAddonMessage)). A compact card fits in one message.

## Prioritized in-game test checklist

Run these in order, because each answer reshapes later milestones. **Priority 1 decides whether the collection works at all.** On a hostile open-world mob in combat during Drain Soul, `/dump issecretvalue()` of `UnitGUID`, `UnitName`, `UnitCreatureType`, `UnitLevel` and `UnitClassification` for `target`. Repeat in a dungeon and for a nameplate-only unit (Q7). In the same session, log `PARTY_KILL` and `UNIT_DIED` payload secrecy, and `UnitIsDead("target")` at the kill (Q10). **Priority 2 decides card art.** Read `GetDisplayInfo()` after `SetUnit("target")` on a hidden PlayerModel. Then render that ID with `SetDisplayInfo` and `SetPortraitTextureFromCreatureDisplayID` after clearing the WDB cache, and compare with `SetCreature(npcID)` (Q11, Q12). **Priority 3 decides capture classification.** Over 20 or more Drain Soul casts, log START and STOP spellIDs, `GetSpellCastSecrecy`, shard deltas while the target is alive versus dead, and the kill-to-`BAG_UPDATE_DELAYED` latency. This measures how often damage shards occur after the November nerf (Q8, Q9). **Priority 4 settles the delete inputs.** Test `/click` on a plain button, a double delete in one press, `C_Item.DeleteItem` from a key press, a combat delete followed by a recount, and WorldFrame OnMouseDown versus OnMouseUp (Q1, Q3, Q4, Q5). **Priority 5 covers the rest.** Test an event-driven soul-bag move in and out of combat (Q6), `ExecuteFrameScript` (Q2), and canvas Settings taint (Q13). Last come conveniences: whether the restriction-forcing CVars work, and whether `AlertFrame.AddQueuedAlertFrameSubSystem` exists for toasts.

## Conclusion

Forever's real constraint is not the hardware-event rule, which every shard addon has already solved. It is the gap between docs that make NPC identity secret by default and observations that it is readable in the open world. Quantum-Seer's collection rests on the observed behaviour holding. Blizzard has said it will bring future UI restrictions to Forever alongside Midnight, so that behaviour could change mid-season. The durable design captures everything readable at cast start and keys cards on data that cannot be revoked: level, classification and a captured displayID. It also treats instance captures as best-effort.

The Forever shard change opens a design opportunity as well. Damage shards give a natural second tier of collectible, an "echo" of a soul that escaped. That separates kills from near-misses more honestly than Soul Journal's ghost and gives duplicates and failures a purpose. With Adventure Journal already owning "kills become shiny cards", Quantum-Seer's lasting edge is likely to come from Warlock-specific mechanics like this rather than from the card frame itself.
